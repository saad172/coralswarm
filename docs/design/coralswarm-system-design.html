Coralswarm
System Design

Coralswarm auto-populates and organizes team documentation as a passive byproduct of normal work. Individuals get a personal knowledge graph built for them from their own work; teams share a queryable reef that anyone can contribute to or pull from. This document is a feature-by-feature technical reference for v1, covering what each system does, how it works, and how it fits together — written for smart outsiders: technical co-founders, engineers, and investors doing due diligence.

Architecture Overview

Coralswarm is a cloud-backed knowledge graph product. People use it through the Next.js web app, the cs CLI, and a remote MCP server at /mcp for AI tools; connectors bring in content from Slack and other platforms. A Rust cloud backend handles ingestion processing, retrieval, and synthesis, and serves the MCP endpoint itself. The data architecture has three roles:

System roles
v1core
Cloud Backend Rust service (Axum + Tokio) backed by Postgres for metadata and Cloudflare R2 for encrypted blob storage. Owns the canonical graph for every user and team. Runs ingestion processing (chunking, embedding, extraction), serves retrieval queries (vector + keyword + graph expansion), and proxies LLM calls. Encrypts data at rest; decrypts during the user's active session to handle queries, then discards decrypted state from working memory.
Clients The Next.js web app and the cs CLI, with native iOS (Swift) and Android (Kotlin) apps on the roadmap. All are thin clients: they own UI, navigation, and auth, and none of them embed the Rust core for retrieval. Queries flow over an authenticated session to the cloud backend, which runs the retrieval pipeline and returns synthesized answers. ADR 0015 (docs/decisions/0015-retire-desktop-app.md) retired the desktop client and its local MCP sidecar on 2026-10-28.
Remote MCP server Served by the cloud backend at /mcp over MCP's streamable HTTP transport. AI tools (Claude Code, Cursor, custom agents) connect to it directly and authenticate with OAuth; nothing runs on the user's machine. Tool calls run the same query and write paths as the web app.
Integration surface Platform add-ins (Zoom, Gmail, Outlook, Meet, Teams) and chat bots (Slack, Teams) talk directly to the cloud backend's ingestion API. The cloud handles the platform API calls, transcript fetches, and message subscriptions. AI tools write through the remote MCP server, and the web app shows the activity feed.

Design principle (v1): The cloud backend is the source of truth. Native clients are UI surfaces over a shared query engine. This is the deliberate v1 architecture — it ships fast, gives Coralswarm production telemetry on the hardest problem (extraction and retrieval quality), and keeps a single code path for retrieval logic across every surface. A future Local Mode premium feature (see v2 Roadmap) will offer fully local retrieval as an option for users who require strict E2E privacy.
🔒
Privacy and data use. Coralswarm's v1 privacy posture is uniform across surfaces and built on two commitments:

1. Encrypted at rest, decrypted only during your active session. User data — personal reefs, team reefs, atoms, nodes — is stored encrypted in cloud blob storage. When a user runs a query, the cloud backend decrypts the relevant portion of their graph in working memory only for the duration of the query (typically seconds), runs retrieval and synthesis, returns the answer, and discards the decrypted state. Persistent storage is never plaintext.

2. No training on user data, period. User content — atoms, nodes, queries, retrieved context, anything in any reef at any scope — is never used to train, fine-tune, or improve any AI model: not Coralswarm's, not any vendor's, not for any product-improvement purpose. Coralswarm uses LLM APIs (Anthropic, OpenAI) on endpoints that operate under no-training defaults. For BYOK mode, the no-training guarantee depends on the user's chosen provider; Coralswarm recommends providers whose terms match this policy.

Team-reef content is encrypted with a per-team key during ingestion; the cloud backend holds the team key in encrypted form and uses it only when authorized team members are actively querying. Team members not in the team's membership list cannot trigger decryption — the access control runs server-side and is enforceable + auditable.

The honest concession: this is not strict end-to-end encryption. A Coralswarm operator with privileged production access could, in principle, observe decrypted content during an active user session. Strict E2E remains available as the future Local Mode premium feature (see v2 Roadmap), for users whose threat model requires that Coralswarm itself never has the capability to view their data.

Core Loop

The product philosophy in one sentence: teams work as normal, and documentation populates and organizes itself as a byproduct of that work. Nothing about how a team writes code, runs meetings, sends email, or coordinates in Slack needs to change. Coralswarm observes the work that's already happening and turns it into structured, queryable knowledge — first for the individual, then for the team if they choose to share it.

This section describes the user journey end-to-end. Everything in the rest of the document is in service of this loop.

The solo loop

A single user, working alone with Coralswarm running in the background.

Solo workflow — personal reef builds itself
v1core
What the user does Connect Coralswarm once (Slack, Gmail, Calendar, optionally a meeting capture toggle). Work as normal. Take meetings, send emails, write in Slack, work with AI tools.
What Coralswarm does Captures content from each source through a platform-native ingestion mechanism, not through background polling:
— Meetings: the user hits "Ingest" in the Coralswarm add-in inside Zoom/Teams/Meet. The add-in triggers the platform's recording and pulls the transcript via the platform API.
— Email: the user hits "Ingest" in the Coralswarm add-in inside Outlook/Gmail. The add-in pulls the thread (and future replies on that thread) via the mail provider's API.
— Chat: the user invites the Coralswarm bot into a Slack/Teams channel or group chat. The bot is a visible member and ingests messages going forward — the group consents by accepting its presence.
— AI tools: the user connects Coralswarm's MCP server to Claude Code, Cursor, etc., and configures a hook that auto-dumps decisions, summaries, or context atoms on session events.
Then: extraction pipeline runs async after each ingestion, building entity, thread, and decision-candidate nodes. Decision candidates surface in a low-friction review queue.
What the user gets A personal reef — a knowledge graph of the user's own work — that they didn't have to write. They can query it ("what did I decide about the auth migration?"), browse it (entity pages, thread summaries), and use it from any AI tool via MCP. All of this without changing how they work.
Privacy boundary The personal reef is the user's private workspace, encrypted at rest in the cloud and accessible only to them. No other user can see it — not their team, not Coralswarm staff in routine operation. The user explicitly chooses what to share to a team reef.

The team loop

Two or more Coralswarm users sharing context with each other. The shared graph is called the team reef.

Team workflow — bidirectional sharing and querying
v1core
Sharing into the reef Explicit promotion: User picks a node (decision, thread, entity) from their personal reef and promotes it to the team reef. One action, one decision, end-to-end encrypted upload.
Co-presence (automatic): When the user ingests content from a shared event (a meeting, an email thread, a Slack channel), the resulting nodes are automatically distributed to every co-present participant who is also a Coralswarm user. One person ingests; the whole room receives. See section 08.
Pulling from the reef Any team member can query the team reef the same way they query their personal one: natural language, hybrid retrieval, cited synthesized answers. Queries can be scoped to personal, team, or both. The MCP server exposes team reef content to AI tools the same way it exposes personal content — with appropriate scope flags.
Adding back to the reef When a team member opens a shared node, they can:
— Add their own atoms linked to that node (a note, a clarification, a follow-up).
— Edit the node (versioned; conflict-resolved per the sync model in section 12).
— Promote one of their own related personal nodes to attach to the existing team node.
The team reef is not a read-only export of one person's brain — it's a shared, growing document of the team's collective knowledge.
Provenance Every atom and every node carries its origin: who ingested it, where it came from, when it was added, who edited it. Nothing in the team reef is anonymous. This matters for trust, for offboarding (section 14), and for resolving disagreements about what was actually decided.

Design implications of the loop

Several design constraints fall out of treating "work as normal → docs auto-populate" as the core loop. They're called out explicitly here because they shape decisions in the rest of the document:

Constraints the loop imposes
Ingestion is volume-heavy "Auto-populate from normal work" means continuous, indefinite, multi-source ingestion. The system has to assume the graph grows forever. See section 05 (Scale & Data Volume) for the projections, limits, and tiering strategy.
Friction in the loop kills it Anything that requires the user to think — "should I save this?", "where does this belong?", "is this worth ingesting?" — breaks the passive-capture promise. Decision candidates are queued, not blocking. Promotion to team is a one-click, not a workflow. Co-presence is automatic, not opt-in-per-event.
No silent ingestion Coralswarm never captures from a private source without a visible consent signal. The signal is mechanism-specific:
— Meetings: hitting Ingest triggers the platform's recording notice (every major platform announces recording to participants).
— Email: the add-in surfaces an in-thread indicator that this thread is being captured; the user with the add-in initiates, but the act is visible in their UI and auditable in the activity feed.
— Chat: the bot is a visible member of the channel. Group consent is established by accepting its presence — same model as a recording bot in a meeting.
— AI tools: the MCP hook is configured by the user explicitly and writes are logged.
Connection establishes authorization; a per-event mechanism establishes action. There is no OAuth-and-poll path that pulls from accounts silently in the background. Opening the Coralswarm app is also not itself an ingestion trigger — the user might open the app to query or browse, and ingestion as a silent side effect of "I launched the window" blurs the consent line. Ingestion happens on explicit triggers (hit Ingest, hit Sync, configure a hook) and on pre-authorized continuous mechanisms (chat bot subscriptions, periodic polling of watched email threads while the app runs).
Personal-first, team-by-consent A user has a working personal reef before they ever share anything. Team sharing is a deliberate act on top of an already-useful product. This is the inverse of most team tools, which require team setup before any individual value.
Provenance everywhere Auto-captured content needs source citations. When the system synthesizes "we decided to use Postgres" from someone's meeting transcript, the user needs to click through to the actual sentence in the actual transcript. Otherwise the auto-documentation is unfalsifiable and won't be trusted.
Bidirectional reef requires conflict handling Multiple users editing the same team node creates merge/conflict scenarios. The data model treats atoms as append-only (no conflict possible), and uses last-write-wins with preserved history on node metadata. See section 12 for the full sync/conflict spec.

04

Tech Stack

Coralswarm's v1 architecture is organized around one Rust cloud backend and several thin native clients. The Rust core lives server-side — it owns Postgres + R2 storage, vector search (sqlite-vec or pgvector), ONNX embedding inference, AES-256-GCM encryption, retrieval logic, and the MCP protocol. Each user-facing surface (the web app and the cs CLI today, native mobile apps later) provides UI, navigation, and auth, calling the cloud backend's APIs for ingestion and query. Platform add-ins (Zoom, Gmail, Outlook, Slack, etc.) are JavaScript shims that signal the cloud backend.

The tradeoff: a single retrieval code path, fast iteration on extraction quality, smaller install sizes, lower hardware floor for users, and production visibility into what queries succeed and fail — at the cost of cloud infrastructure spend and not offering strict end-to-end encryption in v1 (see Privacy and Data Use in the Architecture Overview). A future Local Mode premium feature will re-enable local retrieval for users whose threat model requires strict E2E. See v2 Roadmap.

Rust core
v1core
What it is A Rust crate (cargo workspace with sub-crates) implementing the full retrieval and ingestion pipeline: Postgres + R2 access, vector search, ONNX embedding inference (via the ort crate), AES-256-GCM + X25519 encryption (via ring / rustls), the MCP JSON-RPC protocol, atom/node/graph types, and the LLM orchestration layer.
Where it runs — Cloud backend (primary): the core is the cloud backend. Axum routes wrap it.
— Remote MCP server: part of the cloud backend, mounted at /mcp. Not a separate process.
— CLI: linked as a Rust binary, used in thin-client mode (calls the cloud APIs over HTTP).
The mobile apps (iOS, Android) and the web app do not consume the Rust core directly — they call the cloud backend's APIs. There is one canonical implementation of retrieval, extraction, and encryption logic, and it runs in one place.
Why this matters for v1 Sync bugs, retrieval-quality fixes, and extraction-prompt improvements ship from one deploy. No client update required, no version skew across surfaces, no FFI work for iOS/Android/web. The core can iterate fast on the open question that matters most: extraction and retrieval quality.
Forward path to Local Mode The core is structured so it can be re-targeted to clients (Swift via cbindgen, Kotlin via UniFFI) when Local Mode ships. The retrieval, embedding, and storage logic doesn't change — only the deployment target. That work is real but not on the v1 critical path. See Local Mode in the v2 Roadmap.
ℹ
No desktop client. ADR 0015 (docs/decisions/0015-retire-desktop-app.md) retired the desktop client on 2026-10-28, together with its local MCP sidecar and the backend's local storage mode. Its jobs moved to the web app, the cs CLI, and the remote MCP server at /mcp.

Web app (Next.js)
v1.5
Framework Next.js 15+ with App Router + TypeScript. React Server Components for most pages; Client Components only where interactive (query input, streaming answer rendering). Deployed on Cloudflare Pages or Vercel.
Retrieval model Server-side, like every other v1 client. The browser is a thin client that sends queries to the cloud backend; the cloud does embedding, retrieval, and LLM synthesis, returns the answer. No Rust core in the browser, no WASM, no in-browser SQLite, no in-browser embedding model. Same query path as the CLI and the MCP server.
Why server-side Same reasoning as every other v1 surface: ship fast, single retrieval code path, easy iteration. The pre-Option-C plan had the web running an in-browser WASM bundle for E2E retrieval — that path was abandoned along with local retrieval on every other surface. Local retrieval comes back as Local Mode, not on web first.

CLI
v1
Language Rust, distributed as a standalone binary. cargo install coralswarm-cli for Rust devs; signed binaries via GitHub Releases for everyone else.
How it works Thin client over the cloud backend's API. Authenticates with the cloud backend and sends queries, ingestion commands, and share operations over HTTPS. Requires connectivity — does not have a local graph. Local Mode users will get a CLI variant that talks to the local Rust core directly.
Commands cs query "...", cs context --project X, cs share <node-id> --to team, cs status. Same surface as documented in the Query & Retrieval section.
Cloud backend (Rust)
v1core
Stack Axum (web framework) + Tokio (async runtime) + sqlx (Postgres client) + Postgres for metadata, atoms, nodes, and indexes + Cloudflare R2 for encrypted content blobs. Hosts the Rust core directly — no separate "core library" / "backend service" split.
Role The source of truth for every client in v1. Handles ingestion (chunks atoms, embeds, runs extraction), serves query (vector + keyword + graph-expansion retrieval, LLM synthesis), routes co-presence distribution, manages auth, holds team key material, manages the activity feed and push notifications. The web app, the CLI, and the MCP server all use the same APIs.
Crypto posture User content is encrypted at rest in R2 (AES-256-GCM with per-account / per-team keys). The backend holds the keys in encrypted form, decrypts them in working memory only during authenticated user sessions, and uses them to decrypt graph chunks for retrieval. After a query is served, decrypted state is discarded from working memory. Persistent storage is never plaintext. See Privacy and Data Use in Architecture Overview for the honest framing — this is not strict E2E.
Vector storage Two reasonable options to evaluate before GA: pgvector on Postgres (one fewer system, native to the main store, mature) vs sqlite-vec on per-graph SQLite files in R2 (matches what would run client-side under Local Mode, simpler local/cloud parity). Recommendation: pgvector for v1 — fewer moving parts, better operational tooling. Revisit if Local Mode shipping pushes for cloud/local parity.
Other responsibilities Magic-link auth via Resend. Stores email/user mappings for co-presence lookup. WebSocket push to connected clients for real-time activity and team-reef updates. Outreach email job for non-user co-presence participants. Connector OAuth token storage (encrypted at rest, used server-side to call platform APIs for ingestion).
Hosting Fly.io to start — good fit for Tokio apps, scales horizontally with sticky WebSocket sessions, supports managed Postgres in the same region. R2 lives separately on Cloudflare. Move to AWS / GCP / dedicated infra at scale (likely Enterprise-tier requirement).
What it explicitly does not do Does not act as an LLM proxy (LLM calls go from the backend to Anthropic / OpenAI / BYOK directly). Does not log decrypted user content beyond the in-memory query lifetime. Does not use any user content for training, fine-tuning, or model improvement — Coralswarm's or anyone else's. See Privacy and Data Use.
Native Mac app (Swift)
v1.7–v2
Language & UI Swift + SwiftUI primary, AppKit where SwiftUI falls short (menu bar, vibrancy, native command bar). Shares meaningful UI surface with iOS — same SwiftUI components, same design language — though platform-specific code (menu bar, file integrations) is Mac-only.
v1.7 architecture Ships as a thin client like the web app and iOS — calls the cloud backend's APIs. The native Mac investment in v1.7 is about better macOS feel and integration, not about local retrieval. Local Mode capability is added later (see v2 Roadmap).
Why native Mac at all Better macOS integration than a browser tab can offer: Spotlight indexing, Quick Look previews, Services menu, native menu-bar presence, vibrancy effects, native command-bar UX, proper TCC permission flows. Mac is disproportionately important in Coralswarm's likely beachhead markets (software teams, design teams, creative studios) and these users notice native vs webview-wrapped quality.
Strategic role The Mac native app is the most natural surface for the eventual Local Mode rollout. Mac users on Apple Silicon have the hardware for local embedding inference; the same audience overlaps with the privacy-maximalist segment Local Mode targets. Building Mac native in v1.7 doesn't require Local Mode — but it positions the company to ship Local Mode on Mac first when that time comes.
Distribution Signed + notarized DMG via direct download. Possibly a sandboxed Mac App Store variant later.
Platform add-ins (JS/TS, by necessity)
v1
Why JS Zoom App SDK, Office.js (Outlook), Apps Script (Gmail), Slack Bolt, Microsoft Teams Toolkit — these platforms don't offer Rust SDKs. The add-ins must be JS/TS regardless of the rest of the stack.
What they actually do Thin UI shims. Show the "Ingest" button in the host platform; on click, call the cloud backend's ingestion API with the relevant context (meeting ID, thread ID, channel ID). The cloud backend then pulls the content from the platform API using its stored OAuth tokens. Add-ins themselves carry no user content and no core logic — they're effectively triggers.
Per-platform tech — Zoom: TypeScript + React via the Zoom App SDK
— Gmail: Google Workspace Add-on, Apps Script + CardService
— Outlook: Office.js manifest, TypeScript hosted on CDN
— Slack: Slack Bolt (Node.js) for the bot + Events API + slash commands

Cross-cutting concerns
Embedding model bge-small-en (384 dimensions, ONNX format, ~30MB) loaded into the Rust core. In v1 the model runs server-side only — clients don't carry it. Local Mode will distribute the same model to client devices for on-device inference.
Encryption AES-256-GCM for symmetric encryption of stored content. X25519 for any key-exchange operations. Keys are held server-side, encrypted at rest with envelope keys derived from authentication. The cloud backend decrypts during active user sessions to serve queries. This is not strict end-to-end encryption — see Privacy and Data Use in Architecture Overview. Strict E2E returns as part of Local Mode.
LLM Claude Haiku for extraction (cost-optimized), Claude Sonnet for synthesis (quality-optimized). Managed mode bills through Coralswarm; BYOK mode uses the user's own Anthropic / OpenAI / compatible API key, stored client-side. Local model mode (v1.1) via Ollama. All three modes available from every surface.
Auth Magic link via Resend → device trust token in the OS keychain / Secure Enclave / Android Keystore / browser credential storage. SSO (SAML / OIDC) lands with the Enterprise Layer.
Build & CI Cargo workspace for Rust (core + cloud backend + CLI in one workspace). npm workspaces for the TypeScript code (web app + add-ins). Turbo or Nx for cross-package coordination if needed. GitHub Actions for CI; server releases are GitHub Releases that deploy the backend to Fly.io.
Telemetry PostHog for product analytics, Sentry for error tracking. Telemetry events are scoped to actions and counts (query ran, atom ingested, decision accepted, etc.) — never include user content, query text, or retrieved snippets. Crash reports auto-scrub content fields. Telemetry is opt-out, not opt-in, with a visible toggle in app settings. Aggregated telemetry never feeds model training — same no-training commitment applies.
05

Scale & Data Volume

The core loop is built on the assumption of continuous, indefinite ingestion from many sources. This section makes the resulting data-volume problem explicit: how much data is generated, where it lives, when it stops fitting in the current design, and what we do about it. These projections inform every component below — they are not afterthoughts.

⚠
Single most important number in this document: a heavy individual user generates ~10,000 atoms per year. A 50-person team generating team-reef content at a 20% promotion rate generates ~100,000 atoms per year. At 5 years, that team reef holds ~500K atoms. The design must work at that volume without re-architecture.

Per-user data projections

Atom volume per active user
Working assumptions 5 meetings/week × 30 min avg × 150 words/min = ~22,500 words/week from meetings.
200 Slack messages/week × ~50 words = ~10,000 words/week from Slack.
100 email atoms/week × ~100 words = ~10,000 words/week from email.
AI-tool MCP write-backs: ~20/week × ~200 words = ~4,000 words/week.
Total: ~46,000 words/week ≈ ~60,000 tokens/week ≈ ~120 atoms/week (at 512 tokens/atom).
Annualized ~6,000–10,000 atoms/year for an active user. Lighter users (1 meeting/week, light Slack): ~1,500/year. Heavy users (10+ meetings/week, multiple Slack workspaces): ~20,000/year.
Storage per atom Text content (avg 512 tokens ≈ 2KB UTF-8): ~2KB
Embedding (384d float32, bge-small): ~1.5KB
Metadata (source, timestamps, participants[], scope, hash): ~0.5KB
Index overhead (sqlite-vec + BM25): ~1KB
Total: ~5KB per atom on disk.
Personal reef storage (cloud) Year 1: ~30–50 MB per user in R2. Year 5: ~150–250 MB. Year 10: ~300–500 MB.
At R2 pricing (~$0.015/GB/month): year-5 storage cost per user is ~$0.004/month. Negligible relative to subscription revenue.
Compute (extraction, embedding, query handling) is the cost driver, not storage.
Local cache on client devices Each client (web, mobile) keeps a small encrypted cache of recently-viewed nodes — typically <10MB. Not a full mirror. The cache speeds up app reopen and basic offline browsing but does not support running new queries offline. Local Mode (future premium) is where local full-graph storage returns.

Per-team data projections

Team reef volume
Working assumptions ~20% promotion rate (users share roughly 1 in 5 of their personal atoms to the team reef, mostly via co-presence on shared events).
Co-presence multiplier: when N users are co-present, the same atom is referenced N times in the team reef metadata, but stored once.
Team reef atom count 10-person team: ~12K atoms/year → ~60K at year 5.
50-person team: ~60K atoms/year → ~300K at year 5.
200-person team (v2 territory): ~240K atoms/year → ~1.2M at year 5.
Cloud storage cost At ~5KB/atom and current S3-compatible pricing (~$0.023/GB/month):
10-person team year 5: ~300MB → ~$0.007/month. Negligible.
50-person team year 5: ~1.5GB → ~$0.035/month. Still negligible.
200-person team year 5: ~6GB → ~$0.14/month. Still trivial relative to subscription revenue.
Storage cost is not the constraint. Compute (extraction, embedding, sync) is.
Where team reef data lives All canonical team reef content lives in R2, encrypted at rest. Clients (web, CLI, mobile) do not maintain a full local mirror — they cache recently-viewed nodes only. A 50-person team's 1.5GB at year 5 lives in one place (the cloud), not replicated to every member's machine. This is one of the costs of moving to thin-client architecture removed: no client-side multi-GB cache pressure.

Query latency at scale

sqlite-vec performance and the indexing strategy
Default behavior sqlite-vec ships with brute-force cosine similarity by default — no ANN index. Excellent for correctness, simple to reason about, and fast at modest scale.
Measured break-even On modern hardware (M2 Mac / mid-range Windows CPU), brute-force search over 384d float32 vectors:
— 10K atoms: ~5–10ms per query. Imperceptible.
— 100K atoms: ~50–100ms per query. Acceptable.
— 1M atoms: ~500ms–1s per query. Noticeable, especially with reranking.
— 10M atoms: ~5–10s. Unacceptable.
Mitigation 1 — scope narrowing Every query has a scope filter (personal, team, or specific entity/thread). Apply the scope filter as a SQL WHERE clause before the vector search runs. For most queries this collapses the search space by 10–100x. Implementation: index scope, owner_id, and entity_ids[] as standard SQL indexes; sqlite-vec scans only matching rows.
Mitigation 2 — date partitioning Default query window is "last 6 months" with explicit opt-in to query older content ("include archived"). A simple WHERE created_at > ? clause caps the working set for 90% of queries. Older atoms remain queryable but on demand only.
Mitigation 3 — ANN index at threshold When a graph crosses ~500K atoms (post scope/date filters), the backend opportunistically builds an HNSW index over the active corpus. pgvector supports HNSW natively; sqlite-vec supports it as of v0.1.4 (used in Local Mode). Build runs in background, falls back to brute-force during build, swaps in atomically on completion.
Query budget Target end-to-end latency for a query (embed → retrieve → rerank → synthesize): under 3 seconds at the 90th percentile. Retrieval budget within that: ~500ms. Above 1M atoms, the synthesis call (Sonnet) dominates anyway — context window assembly and LLM TTFT are the real ceiling.

Tiering & retention

Hot / warm / cold tiers
Hot (in-memory cache on backend) Atoms accessed or created in the last 90 days. Decrypted segments cached in the cloud backend's working memory per active user session, indexed and ready to query. Most queries are served entirely from hot tier.
Warm (Postgres + R2, on-demand decrypt) Atoms 90 days to 2 years old. Stored encrypted in R2; metadata indexed in Postgres. First query touching this tier in a session pays a small decrypt + load cost (~100ms).
Cold (compressed R2 archive) Atoms older than 2 years. Compressed (zstd) to ~20% original size, moved to R2's infrequent-access tier. Embedding kept but stored separately from text. Queryable on explicit "include archived" flag; otherwise excluded from default retrieval.
Retention defaults Personal reef: indefinite by default. User can configure auto-delete-after-N-years per source type (e.g., "delete Slack atoms older than 1 year").
Team reef: retention is a team-admin setting. Default: indefinite for decision/entity/thread nodes; auto-archive Slack/meeting atoms after 2 years (the node persists, the underlying atoms move to cold).
Hard delete: deletes are immediate in the cloud and surface to clients on next refresh. Client-side caches honor server-issued deletion markers.
Why tiering matters A 5-year user with 50K atoms only has ~12K hot atoms in active rotation. The backend caches working sets per user (LRU eviction across users), keeping query latency stable as the long tail of historical content grows.

Background pipeline throughput

Extraction and embedding pipeline capacity
Embedding throughput bge-small ONNX on CPU: ~50–200 atoms/second batched, depending on hardware. A user's daily ingestion (~25 atoms) embeds in well under a second. A 1-hour meeting transcript (~120 atoms) embeds in 1–3 seconds. Embedding is never the bottleneck.
Extraction throughput Claude Haiku at current rate limits: ~50 atoms/minute per user under default API tier. A daily batch of 25 atoms processes in 30 seconds. Heavy backfill (initial connector ingestion of 6 months of Slack history) can produce 10,000+ atoms in a burst; the extraction pipeline runs against a bounded queue with backoff to stay under rate limits. Heavy backfills complete in 2–6 hours.
Cost at scale Per active user at heavy use (10K atoms/year): ~$20/year in extraction costs (Haiku) + ~$30/year in synthesis costs (Sonnet, 20 queries/week × $0.03/query × 50 weeks).
Total managed-mode LLM cost per heavy user: ~$50/year. Subscription pricing must support this — early ballpark: $20/user/month team-plan = $240/year, leaving healthy margin even at heavy use.
BYOK and local-model modes shift this cost off Coralswarm entirely.
Backpressure Ingestion writes atoms to Postgres + R2 quickly. Extraction reads from a per-user job queue (Postgres-backed or Redis) and runs async with concurrency limits. If extraction falls behind (e.g. during a backfill), atoms remain queryable via vector search — the LLM-derived entity/thread/decision nodes just trail by minutes to hours. The user always has access to raw atoms, even if they haven't been "processed" yet.

Re-indexing and migrations

Handling embedding model upgrades and schema changes
Embedding model upgrades When the embedding model changes (e.g. bge-small → a better successor), every atom needs to be re-embedded. At 200 atoms/sec on backend workers, a 50K-atom personal reef re-embeds in ~4 minutes. A 1M-atom team reef re-embeds in ~80 minutes. Re-embedding runs as a backend job, in chunks; the old embedding remains authoritative until the new one is built. No client-side work, no client downtime. Local Mode users will need to re-embed locally on their devices when they upgrade — that's a future consideration.
Embedding dimensionality is a schema lock Both pgvector and sqlite-vec require fixed vector dimensions at table creation. Choice of 384d (bge-small) vs 768d (nomic-embed) is permanent for a graph unless we run a full migration. Decision needs to be made before v1 GA — see Open Questions. Recommendation: 384d for v1 (faster, smaller, good enough); leave a clean migration path to 768d for v2 if quality demands it.
Schema migrations Backend Postgres migrations run on deploy via sqlx-migrate. Each migration is idempotent and reversible where possible. Client surfaces (web, CLI, mobile) receive new schemas through the API — no client-side migrations needed since clients don't own canonical state.

What breaks first

An honest list of failure modes ordered by when we expect to hit them, given the projections above:

Scale failure modes, ranked
1. Initial connector backfill UX A user connects Slack with 5 years of history. The extraction pipeline produces 50K+ atoms in a single backfill. This is the first scale wall most users hit — within hours of signup. Mitigation: bounded backfill window (default: last 90 days) with explicit "import historical" action for older content.
2. Query latency on large team reefs At ~500K atoms in a team reef, brute-force similarity search starts to feel slow. Mitigation: scope narrowing + date partitioning (described above). The HNSW index is the v1.x backstop if those don't suffice.
3. Backend compute concurrency at peak Under cloud-primary retrieval, every query touches backend compute (decrypt, embed, retrieve, synthesize). At ~1,000 concurrent active users each issuing a query every few minutes, the backend needs to handle ~10–50 queries/second sustained, with bursts higher. Mitigation: stateless query workers behind a load balancer + autoscaling on Fly.io. Embedding inference is the per-query CPU hot path — batched across users when possible. Worth a load-test pass before paid-tier launch.
4. LLM cost at the long tail A small number of very heavy users drive disproportionate LLM spend. Mitigation: per-user budgets in managed mode with soft caps + nudge to BYOK or local-model mode if exceeded consistently.
5. R2 egress and decrypt overhead on team queries A large team where many members are querying simultaneously means the backend is decrypting overlapping team-reef segments. Mitigation: shared decrypted working sets in backend memory (one decrypt serves N concurrent team-member queries), R2 read caching at the backend layer. Not a v1 problem; will become one as teams scale past 100 members.

Ingestion Engine

The ingestion engine receives content from external sources, chunks it into atoms, generates embeddings, and writes atoms to the user's encrypted reef storage in the cloud. Under v1's cloud-primary architecture the engine runs in the cloud backend — platform add-ins and chat bots call its ingestion API directly; AI tools write through the remote MCP server, which calls the same ingestion path. There is no OAuth-and-poll silent connector path — every external source connects through a platform-native mechanism that surfaces ingestion as a visible, in-context act. Three modes cover the v1 surface.

Mode 1 — Platform add-ins (meetings & email)

The user installs a Coralswarm add-in inside the source platform — Zoom, Microsoft Teams, Google Meet, Outlook, Gmail. The add-in is the UI surface for ingestion: a button the user presses inside the platform where the content lives. When pressed, the add-in calls the platform's API to fetch the underlying content (or trigger a recording, in the case of meetings).

Meeting add-in — Zoom / Teams / Meet
v1privacy-critical
What it does During a live meeting, the user clicks the Coralswarm Ingest button in the platform's add-in surface (Zoom App Marketplace, Teams app, Google Workspace add-on). The add-in triggers the platform's native recording / transcription via API. When the meeting ends, the add-in fetches the resulting transcript from the platform API and pipes it into the local ingestion engine as atoms.
How it works 1. User clicks Ingest inside the Zoom/Teams/Meet add-in.
2. Add-in calls the platform's API to start recording and request a transcript. The platform shows its standard recording notice to all participants (this is the consent signal).
3. Coralswarm's cloud backend polls the platform API for transcript availability (using OAuth tokens authorized at install time). Most platforms make the transcript available within minutes of meeting end.
4. Transcript pulled via API, chunked into ~512-token atoms with speaker attribution from the platform's metadata.
5. Atoms embedded server-side and written to the user's encrypted reef storage. Extraction pipeline runs async to suggest thread / entity / decision nodes.
Consent model Relies on the meeting platform's own recording notice — every major platform announces and indicates recording to participants by policy. This satisfies two-party consent in CA, FL, IL, MD, etc. by the same mechanism that any other recording action in Zoom/Teams/Meet does. The user doesn't need to send a separate notice.
Audio handling Coralswarm does not capture audio locally. The audio stays inside the meeting platform's pipeline. Only the resulting transcript (text) leaves the platform, on a per-meeting user-triggered basis. This is a deliberate scope choice: the platforms already have the audio; Coralswarm doesn't expand the surface area.
v1 platforms Zoom (Marketplace app + transcript API), Microsoft Teams (Teams app + Graph API for transcripts), Google Meet (Workspace add-on + Meet transcript API, requires Workspace Business Standard+).
Out of scope for v1 In-person meetings, audio-only calls, meetings on platforms without a transcript API. These are addressed by the v1.x screen-recording + Whisper fallback path (committed — see v2 Roadmap and Open Questions). v1 ships with platform-API capture only.
Email add-in — Outlook / Gmail
v1
What it does User opens a thread in Outlook or Gmail and clicks Ingest in the Coralswarm add-in (Outlook add-in pane / Gmail add-on). The add-in calls the mail provider's API (Microsoft Graph for Outlook, Gmail API for Gmail) to fetch the thread's content and registers the thread for ongoing capture.
How it works 1. User clicks Ingest inside the email client's add-in pane.
2. Add-in calls the mail provider's API with the thread ID.
3. Current thread state (subject, participants, all messages to date) pulled and ingested as atoms.
4. The thread ID is added to the user's "watched threads" list. New replies on the same thread are ingested automatically (per the mail provider's push or polling-on-trigger model) until the user explicitly un-watches.
5. The add-in pane surfaces an indicator that this thread is being captured, visible to the user every time they open it.
Future replies Once a thread is ingested, future replies on it flow in automatically — the user has signaled that this thread is in scope. Mechanism: the cloud backend maintains a per-user watched_threads list and polls each thread via the mail provider's API (Gmail / Graph) using the user's stored OAuth tokens, on two triggers: (1) a periodic cadence (~10–15 minutes) regardless of whether any Coralswarm client is open, and (2) on demand via a "Sync this thread now" action in the email add-in. App launch is deliberately not a trigger — opening a client is not, by itself, an ingestion intent. The user can un-watch a thread at any time. Threads not explicitly ingested are never touched.
Consent boundary Honest disclosure: other recipients of an email thread are not notified that one party has ingested it through Coralswarm. This is the same posture as forwarding, BCC-archiving, or copying-into-Notion — a recipient's own copy of content they were sent is theirs to capture. Coralswarm doesn't take this further: it does not analyze contacts, summarize unread mail, or pull anything the user has not actively chosen to ingest.
v1 platforms Outlook (Microsoft 365 add-in via Office.js + Graph API), Gmail (Workspace Marketplace add-on via Gmail API). Both desktop and web mail clients supported through the same add-in.

Mode 2 — Chat bots

For team chat platforms (Slack, Microsoft Teams chat, Discord), Coralswarm runs as a bot user. Someone with admin or workspace rights installs the bot at the workspace level; individual channels opt in by inviting the bot. Once invited, the bot ingests messages in that channel from the moment of invite forward. The bot's presence in the member list is the consent signal — every person in the channel can see it's there.

Chat bot ingestion
v1privacy-critical
What it does Once invited to a Slack channel, Teams chat, or Discord channel, the Coralswarm bot subscribes to new messages via the platform's events API. Each new message becomes an atom in the inviting user's personal reef (and, by co-presence, in the personal reefs of any other Coralswarm users in the channel). No historical backfill from before the invite — the bot ingests from invite-time forward only.
How it works 1. Workspace admin installs Coralswarm as an app at the workspace/server level (one-time OAuth at install time, scoped narrowly to messages.read on channels the bot is invited to).
2. A user invites the bot to a specific channel (/invite @coralswarm in Slack, "Add member" in Teams, etc.).
3. The bot subscribes to that channel's message events via the platform's webhook/socket API.
4. Each new message: streamed to the inviting user's local Coralswarm client, chunked into an atom (one message = one atom typically), embedded, stored.
5. The bot posts a one-time message on invite: "Coralswarm is now capturing this channel for [inviting user]. Anyone can /coralswarm-pause to stop." So everyone sees the intent.
Consent model The bot is a visible member of the channel. Group consent is established the same way as a meeting bot: everyone sees it, anyone can object, the inviting user takes responsibility for its presence. This is the model platforms like Otter, Read, and Granola already use for meetings — generalized to chat.
Scope & control Bot only ingests from channels it's invited to. Never DMs unless invited to a group DM.
Any channel member can /coralswarm-pause or remove the bot.
Coralswarm doesn't index private or admin-only channels unless the bot is explicitly added.
The bot identity (display name, avatar) is consistent across workspaces — recognizable as a Coralswarm bot, not disguised.
v1 platforms Slack (Apps + Events API), Microsoft Teams (Bot Framework + Graph API), Discord (deferred to v1.x — different consent norms in Discord communities). DMs not supported in v1.

Mode 3 — AI tool capture (MCP + hooks)

The remote MCP server is bidirectional. AI tools the user has connected — Claude Code, Cursor, Cowork, custom agents — can read context from Coralswarm and write context back to it. User-configured hooks define when the AI tool should auto-dump data, eliminating the need to manually save context at the end of each session.

Bidirectional MCP ingestion
v1core
What it does When an AI tool reaches a decision, finishes a task, or hits a configured hook event (session end, branch checkout, file commit, etc.), it writes a context atom back to Coralswarm via MCP. The personal reef grows from AI-assisted work the same way it grows from meetings and email.
MCP write surface write_context(content, type, metadata) — generic context atom write.
suggest_decision(title, rationale, alternatives) — queue a decision candidate for user review.
append_to_thread(thread_id, content) — extend an existing thread with new context.
Hook configuration Users configure hooks per tool. Common patterns:
— Claude Code: hook on session end → dump a session summary, list of files touched, and any decisions reached. Hook on Stop events → write a final-state atom.
— Cursor: hook on commit → write a "what changed and why" atom linked to the commit.
— Custom agents: any agent calling MCP can be configured to dump on its own task-completion events.
Hooks are defined in the AI tool's own configuration (Claude Code's settings.json hooks block, Cursor's rules file, etc.), pointing at Coralswarm's MCP server.
User control MCP write permissions are granted per-tool, separately from read permissions. Every write surfaces in the live activity feed with a "see what was written" link. The user can revoke write access at any time without losing previously-written content.

Knowledge Graph

The knowledge graph is the core product surface. It transforms raw atoms into structured, queryable nodes — and maintains the relationships between them. Two processes build the graph: the extraction pipeline (automatic) and user curation (manual).

Extraction pipeline
v1core
What it does After atoms are stored, an async background pipeline runs LLM-powered extraction to identify entities, threads, and candidate decisions from the new atoms. Entities and threads are created automatically. Decision candidates are queued for user review.
Entity extraction LLM prompt identifies named entities (people, companies, projects, systems) in new atoms. Resolves aliases (e.g. "the Henderson client" → existing "Henderson" entity). Creates new entity node if no match. Links atom to entity via atom_ids[].
Thread extraction Groups atoms by source event (a meeting = one thread, an email thread = one thread, a Slack channel session = one thread). Generates a short LLM summary stored as thread.summary. Links all atoms from the event to the thread node.
Decision candidates LLM prompt looks for decision-shaped content in atoms: "we decided / we chose / we're going with / we're not doing X because." Extracts title, rationale, and alternatives. Queues as a candidate — does not create a decision node until user approves.
LLM used Claude Haiku (default) for cost efficiency. Extraction prompts are small and well-structured. Estimated ~$0.002 per meeting hour of extraction at current Haiku pricing.
User curation interface
v1
What it does Surfaces decision candidates in a review queue. User accepts (with optional edits), rejects, or marks as "not a decision." Also allows manual node creation, entity merging, and graph editing.
Decision review Notification badge on the Coralswarm icon when new candidates are queued. Review UI shows: candidate title, extracted rationale, source atoms (with context), and the option to edit any field before accepting. Rejections feed back as negative examples to improve future extraction.
Manual creation User can create any node type directly: "New Decision," "New Entity," "New Reference." Manual nodes can be linked to existing atoms or created standalone.

Temporal Memory

Coralswarm's knowledge graph grows over time, and time matters in how it stays useful. Three temporal behaviors are first-class in v1: recency-staged answers (every claim is dated so the user knows how fresh it is), contradiction handling (when two pieces of data disagree, the system picks the newer by default but surfaces the assumption for the user to confirm or reject), and entity drift (entities whose description has shifted over time are flagged on their entity page). Together these turn the graph from a static accumulation of atoms into something that ages well.

Underlying all three: the decided_at field on decision nodes is mandatory in v1, sourced from the underlying event timestamp (meeting time, Slack message time, email send time) rather than from when the extraction pipeline ran. Manual override exists for cases where the source-event time isn't the actual decision time, but the default is source-event. This is the field the entire temporal layer depends on being honest.

Recency-staged synthesis
v1core
What it does Every synthesized answer surfaces timestamps inline with its claims. "We're using Paddle" becomes "We're using Paddle (decided 1 week ago)." The user weighs recency against whether the claim is fresh or stale in their context — the system doesn't assume on the user's behalf.
How it works The retrieved-context block passed to the synthesizer carries each atom's and each node's relevant timestamps (atom.timestamp for raw content, decision.decided_at for decisions, thread.date_range for threads). The synthesis prompt instructs the LLM to surface those timestamps inline with the substantive claims they support. No new data model, no retrieval-time work — a synthesis-prompt change only.
Why it matters RAG products commonly answer with full confidence from material of unknown age. The user can't tell if "we're using Stripe" was decided yesterday or 18 months ago. Surfacing the age makes the answer honest and lets the user override the system's implicit recency judgment when their domain knowledge says the older claim is still operative.
Contradiction handling
v1core
What it does When retrieval surfaces two pieces of data that disagree on the same point — "we're using Stripe" from 3 weeks ago and "we're using Paddle" from 1 week ago — the system picks the newer for its answer, surfaces the assumption inline, and offers a one-click confirm or reject. Confirmed supersessions become permanent edges in the graph; rejections become permanent non-supersession markers. Future queries get cleaner.
Default behavior Newer wins by default — never older wins, never both shown without commentary, never a refusal to answer. The system commits to an answer, and is transparent about the assumption that drove it. Recency is the right default for "what's currently true" queries, which is the dominant query shape. The newer-wins assumption is occasionally wrong, which is why the inline confirmation exists.
Data model additions Two new tables, kept separate from the node schema so the temporal layer is cleanly composable:

supersession_edge — one row per confirmed supersession. Fields: superseded_id, superseder_id, confirmed_by, confirmed_at, source ('suggested' when accepted from an inline prompt, 'manual' when a user explicitly creates one).

non_supersession_pair — one row per pair of nodes the user has marked as not in a supersession relationship. Order-insensitive. Fields: node_a_id, node_b_id, marked_by, marked_at. Without this, the same prompt fires every query for the same pair — fatigue.
Retrieval changes One new step in the retrieval pipeline (see section 10), inserted between graph expansion and rerank: contradiction detection. For the retrieved node set, find pairs that (a) share an entity, (b) have substantively different content on the same point, (c) don't already have a supersession_edge, (d) aren't in non_supersession_pair. Pass any flagged pairs to the synthesizer.

Detection itself happens inside the synthesis LLM in v1 — the synthesis prompt asks for structured output that includes a contradiction_suggestions field alongside the answer. If quality suffers at scale, upgrade to a dedicated Haiku pre-pass before synthesis. Unlikely to be needed at typical retrieval set sizes of ~10 nodes.
UX Inline below the answer, when a contradiction was detected:

"Paddle (decided 1 week ago) — appears to replace Stripe (3 weeks ago). [Replaces Stripe]  [These are separate]"

[Replaces Stripe] writes a supersession_edge; future queries auto-resolve to the newer node, with the supersession shown as historical context. [These are separate] writes a non_supersession_pair; future queries continue to surface both but don't re-prompt about their relationship.
No proactive surfacing v1 deliberately does not notify users about contradictions outside of query context. The system doesn't ping you to say "I noticed two contradicting decisions about auth, review?" If you never ask, the contradiction sits in the graph as latent. This is a constraint, not an oversight — proactive notifications fight the passive-capture promise. Easier to add later than to remove.
Entity drift
v1
What it does When the user opens an entity page and that entity's recent atoms describe it substantively differently than its older atoms, surface a "this entity's description has shifted" indicator with an optional "see evolution" timeline view. The user can read the evolution, manually fork the entity into two if the shift was actually a rename (e.g., "Project Atlas" → "Atlas Migration"), or ignore the indicator.
How it works Computed at view time, not at ingest time. When the user opens an entity page, the backend (a) collects the entity's atoms split by date — last 90 days vs. older, (b) generates a brief LLM summary of each half, (c) embeds both summaries and computes cosine distance. If the distance crosses a threshold (TBD, see Open Questions), the drift indicator shows. No background job, no stored state, no retrieval-time impact.
Why lazy Drift is the lowest-leverage of the three temporal behaviors — most users don't think about it most of the time. Computing it eagerly at ingest time would waste compute on entities no one revisits. Computing it lazily at view time keeps the cost proportional to actual user interest.
No automatic forking The system never forks an entity automatically. Even when drift is detected, the action is a flag, not a structural change. The user decides whether the drift represents the same entity evolving or two entities that should be split. Auto-forking would create silent graph mutations the user can't predict — and that breaks the trust the rest of the design works to earn.
ℹ
What's deliberately not in v1. True bitemporal modeling (separating valid time from transaction time), point-in-time entity reconstruction ("show me Henderson as of March"), and automatic entity-state-at-date computation. These are real features for an audit or compliance product; they're heavy and they're not what the v1 use case demands. The three behaviors above cover the daily workflow — knowing how old something is, resolving conflicts when they arise, and noticing when meaning has shifted. The heavier temporal features land in v2 or later if customer conversations push for them.

Co-presence Sharing

Co-presence is the mechanism that automatically distributes context to all participants of a shared event — without requiring any explicit sharing action. It's the viral loop: one user ingests, everyone benefits.

Co-presence distribution
v1core
What it does When an atom is ingested from a shared event (meeting, email thread, group chat), the ingestion engine identifies all co-present participants from the source metadata. Any participant who is a Coralswarm user receives a copy of the resulting nodes in their personal graph.
How it works 1. Ingestion engine extracts participants[] from source metadata (calendar attendees, email recipients, Slack channel members).
2. Looks up each participant email against the Coralswarm user directory (cloud lookup — just email → user_id mapping, no content shared yet).
3. For each matched user: the thread/entity nodes generated from the atoms are queued in that user's co-presence inbox on the cloud backend (encrypted).
4. When the matched user opens Coralswarm, their client decrypts and syncs the co-presence nodes into their personal graph.
5. Nodes land with source: copresence so the user knows the origin.
Opt-out Any co-presence node can be deleted from the personal graph at any time. Deletion is local — doesn't affect the originating user's copy or other participants' copies.
Outreach to non-users When the participant lookup returns an email address that doesn't match any Coralswarm user, the email is added to an outreach queue. Coralswarm sends that address a value-proposition email — "you've been in N meetings / M threads where colleagues are documenting context. Sign up for a 7-day free trial to access them." The email contains no captured content; the actual material surfaces only after authenticated signup. Cadence: one email on first co-presence event per recipient, weekly digests after, auto-stop at 4 weeks without conversion. See Open Questions for the full pricing decision.
Backfill on signup When a new user signs up — whether from a Coralswarm outreach email or organically — the system queries the co-presence inbox for all events where colleagues have already ingested content they were part of. User sees a consent screen during onboarding: "You were in 12 meetings and 4 email threads your colleagues ingested. Import?" Accepts per-item or in bulk. New signups get 7 days of full paid-tier access (cloud sync + mobile + web) so they experience the backfill on the surfaces it's most valuable on. At trial end, account converts to paid or drops to the free tier with an export option.
Privacy boundary Co-presence is based on who was present, not who was mentioned. If a meeting discusses Bob but Bob wasn't on the invite, Bob receives nothing. Subjects ≠ participants.
🔒
Security model: Co-presence routing happens entirely server-side under v1's cloud-primary architecture. The cloud backend matches event participants against the Coralswarm user directory, queues the resulting nodes against each recipient's encrypted reef, and serves them on the recipient's next query. The encryption posture is the same as any other reef content (see Privacy and Data Use). Co-presence under Local Mode (future) shifts to the recipient's device decrypting bundles delivered from the cloud.

Query & Retrieval

Coralswarm exposes three query surfaces: the web app's query bar, the MCP server (for AI tools), and the CLI. All three pathways flow through the same retrieval engine in the cloud backend.

Retrieval engine
v1core
What it does Takes a natural language query. Returns a synthesized answer with citations linking to the source nodes and atoms. Uses a hybrid retrieval strategy: vector similarity search + keyword search + graph traversal.
Where it runs Cloud backend (Rust). All v1 clients submit queries over an authenticated session and the backend handles the pipeline end-to-end. Decryption of the relevant graph chunks happens in working memory for the duration of the query and is discarded afterward — see Privacy and Data Use in Architecture Overview. Local Mode (future) re-localizes the same pipeline to user devices.
Retrieval steps 1. Embed the query using the embedding model in the cloud backend.
2. Vector search against atom embeddings (pgvector / sqlite-vec). Returns top-K atoms by cosine similarity.
3. Keyword search (BM25) against atom content for exact-match boost.
4. Graph expansion: for each returned atom, fetch its parent node and sibling atoms (same thread, same entity). This surfaces context the vector search alone would miss.
5. Contradiction detection: look for pairs of retrieved nodes that share an entity, have substantively different content on the same point, and aren't already linked by a supersession_edge or non_supersession_pair. Pass flagged pairs to the synthesizer. See section 08 for full design.
6. Rerank the expanded context by relevance + recency.
7. Synthesize using the LLM: prompt includes the top context chunks + the original query + any flagged contradictions. Returns an answer with in-line citations to source nodes, inline timestamps on substantive claims, and structured contradiction_suggestions when applicable.
Scope control Queries run against the user's personal reef by default. User can specify scope: team or scope: all. Team-reef access is enforced server-side against the user's team membership — only authorized members can trigger team-reef decryption + retrieval.
Citation format Every claim in the synthesized answer is linked to its source node (decision / thread / entity) and the specific atom it came from. Users can click through to see the original content in context.

LLM Layer

Coralswarm uses LLMs for three tasks: extraction (building nodes from atoms), synthesis (answering queries), and the in-app conversational interface. The LLM layer is configurable — users can query Coralswarm directly through the app, or connect their own API keys.

LLM configuration
v1
Managed mode Default. User queries Coralswarm directly through the app interface. Coralswarm makes LLM API calls on the user's behalf using a managed key. Billed as part of the subscription. Simplest onboarding — no API key required.
BYOK mode User connects their own Anthropic, OpenAI, or compatible API key. Stored in OS keychain. All LLM calls route through the user's key. Useful for power users with existing API contracts or who want full cost visibility.
Local model mode (v1.1) Power users running a local LLM via Ollama on a machine the cloud backend can reach (or via a future Local Mode build that runs the entire pipeline on-device). v1 default sends LLM calls from the cloud backend to whichever provider the user has configured.
Model defaults Extraction: Claude Haiku (fast, cheap, structured output). Synthesis: Claude Sonnet (better reasoning, worth the cost for query answers). Embeddings: bge-small-en running server-side in the cloud backend's Rust core (v1). Local Mode users will run embeddings on-device.
Cost estimate ~$0.002/meeting hour for extraction (Haiku). ~$0.01–0.05/query for synthesis (Sonnet, depending on context size). An active user ingesting 5 meetings/week and running 20 queries/week costs approximately $0.30–0.60/week in LLM costs at current pricing.

Team Graph Sync

The team graph is shared context across team members. Under v1's cloud-primary architecture, the team graph lives in the cloud backend as the canonical store; clients (web, CLI, MCP) query it through the same retrieval API they use for personal reefs, with team scope. There is no client-to-client peer sync — every read or write goes through the backend.

Team graph architecture
v1
What it does When a user promotes a node to the team reef, or when co-presence distribution creates team-scoped atoms, the cloud backend writes the content to team-scoped storage (encrypted with the team key) and broadcasts an update event to connected team members' clients. Team members querying the team reef hit the same backend retrieval engine, scoped to their team's data.
Encryption model Team has a per-team symmetric key (AES-256-GCM) generated by the cloud backend on team creation. The key is stored encrypted at rest, wrapped in an envelope key tied to team-member authentication. When an authorized team member queries the team reef, the backend unwraps the team key in working memory, decrypts the relevant atoms, runs retrieval, and discards the unwrapped key. The honest framing: the backend has the capability to decrypt team content; access control governs when it does. Not strict E2E — see Privacy and Data Use in Architecture Overview.
Access control Team membership is checked server-side on every team-reef query and write. A user removed from a team loses access immediately on next request — no propagation lag, no possibility of stale client cache letting them in. Team admins manage membership in the web app.
Conflict resolution Backend-mediated. Atoms are append-only (no conflict possible). For node metadata edits, the backend serializes writes — last write wins at the record level, with full version history kept. If two users edit the same decision node within seconds, both versions are preserved and the second user sees a "this was just edited by [name]" prompt before their change is applied.
Real-time updates WebSocket push from the cloud backend to connected clients on team-reef changes (new nodes, edits, co-presence arrivals). When a client is offline, updates accumulate server-side and are surfaced on reconnect.
Offboarding When a team member is marked as departed: their personal reef stays theirs (exportable on request via the cloud backend, then deletable). Their contributions to the team reef remain — provenance is preserved. They lose access to team-reef queries immediately. The team key is rotated by the backend automatically; clients of remaining members never see the rotation.
Local Mode interaction (future) Local Mode users running fully on-device will receive team-reef content as encrypted bundles synced from the cloud backend, decrypted client-side. Effectively the v1-era E2E team-sync model, only enabled for users who opt into Local Mode. Mixed teams (some members on Local Mode, some not) work: the cloud backend serves both query paths from the same canonical store.

Connectors

"Connectors" in Coralswarm v1 are not a unified abstraction — they are platform-specific integrations falling into three categories that match the three ingestion modes (section 06): platform add-ins (meeting + email clients), chat bots (team chat platforms), and AI tool integrations (MCP servers + hooks). Each category has different installation, authorization, and event-flow mechanics. Listing them per-category rather than under a single interface reflects the reality of the integration surface.

Why no unified connector interface
Add-ins Live inside the source platform's UI (Zoom App Marketplace, Office.js, Workspace add-on). Distribution and review go through the platform's app store. Authorization is platform-mediated. Event flow is user-triggered API calls. No polling.
Chat bots Live as a workspace-installed app + bot user. OAuth at install time, scoped to message events on invited channels. Event flow is webhook/socket subscriptions to channel messages.
AI tool integrations Coralswarm exposes an MCP server; AI tools connect to it. Event flow is programmatic — the AI tool calls Coralswarm's MCP write tools when its own configured hooks fire.
Why these don't share an interface An add-in is a UI extension; a bot is a server-side event subscriber; an MCP integration is a peer-to-peer protocol. Forcing them under one ConnectorInterface abstraction would add code complexity without simplifying anything — the user-facing concepts and the integration mechanics genuinely differ.

Local Screen Recording + Whisper Capture (v1.x)

A universal meeting capture path independent of any platform's transcript API. Targets the gap the v1 platform-API model leaves: in-person meetings, audio-only calls, platforms without transcript APIs (Webex, GoToMeeting, smaller tools), users on platform tiers that don't include API access, and users who want their meeting audio never to touch a third-party cloud.

What it does: User hits Ingest in the Coralswarm app (not in a platform add-in). A local client captures system audio via the OS audio API — ScreenCaptureKit on Mac, WASAPI loopback on Windows. No such client exists since ADR 0015 retired the desktop client, so this path needs a new host before it can ship. Audio is then transcribed via Whisper, with two viable design options under v1's cloud-primary architecture (see Open Questions): (a) stream audio to the cloud backend over an authenticated channel, transcribe server-side. (b) Transcribe on-device with whisper.cpp (Metal acceleration on Mac, ONNX on Windows); only the transcript leaves the device. Option (b) is the stronger privacy story; option (a) is the simpler install and works well on weaker user hardware. Transcript chunked into atoms the same way as the API path.

Trade-offs vs the v1 platform-API path: Hardware-dependent (Whisper Small on an M2 Mac runs near real-time; on a 5-year-old i5 with no GPU it can run 5–10x slower than real-time). Speaker attribution is worse — no platform metadata, so attribution comes from diarization in Whisper which is rougher. Privacy is stronger — audio never leaves the user's machine. Two-party consent burden shifts to Coralswarm: the app must send a visible recording notice (in-app banner + optional bot-posted Slack/Teams message) before capturing, since the platforms aren't doing it.

Open implementation question: bundle the Whisper model with that client (~100–500MB depending on size) or download on first use? Bundled is faster on first capture and works offline; lazy-download keeps the v1 binary small. Leaning toward lazy-download with a "warm up" prompt when the user first enables this capture mode.

Web app architecture
v1.5

What the cloud does On each query (identical to the CLI and MCP paths):
1. Client sends the query string over an authenticated session.
2. Cloud fetches the user's encrypted graph chunks from R2, decrypts them in working memory.
3. Cloud runs embedding inference on the query.
4. Cloud runs vector + keyword + graph-expansion retrieval.
5. Cloud sends retrieved context to the LLM API (Sonnet, BYOK, etc.) for synthesis.
6. Cloud returns the synthesized answer with citations.

Org Graph

A third scope layer above Team. Nodes promoted to the Org graph are accessible to all members of the organization. Requires an admin console for governance, an IT-friendly deployment model, and stricter audit logging. This is the enterprise play — but it's built on top of the individual-first architecture, not replacing it.

Key design question: Who can promote to the Org graph? Only admins? Any team? Any user? This is a policy decision that will depend on what enterprise buyers ask for in v1 design partner conversations.

Conflict Detection

When the same entity or topic has conflicting decisions across time ("we chose Postgres in March, Redis in October"), the system surfaces the conflict and shows both decisions with their timestamps and provenance. Requires a semantic similarity pass across decision nodes — a scheduled job that runs weekly and flags conflicts for user review.

Freshness Signals

Nodes decay in relevance over time. A decision made 3 years ago in a fast-moving domain may no longer be current. Freshness signals add a staleness indicator to nodes based on: time since creation, time since any related atom was added, and explicit user "this is still current" confirmations. Surfaces stale nodes for review before they're surfaced in query answers.

Enterprise Layer

SSO (SAML / OIDC), SOC 2 Type II, audit logs, data residency options, admin console, DLP controls, API for HR system integration (auto-trigger offboarding on termination). This is what unlocks $50K+ annual contracts. Estimated 6-9 months after v1 GA given the certification timeline for SOC 2.

Local Mode

Local Mode is the future premium feature that restores strict end-to-end encryption by running the full retrieval pipeline on-device. It's the answer to "what about users whose threat model can't accept any server-side decryption capability." Not a v1 feature — but the v1 architecture is structured so Local Mode is an addition, not a rewrite.

Local Mode
v2+privacy
What it does Personal-reef storage, embedding inference, and retrieval all run on the user's device. The cloud backend stores ciphertext only for that user's personal reef and never holds the decryption key. Team-reef content is delivered as encrypted bundles, decrypted on-device with team keys held client-side. The on-device pipeline produces identical retrieval results to the cloud pipeline — it's the same Rust core, just re-targeted.
Privacy posture Strict end-to-end. The cloud backend has zero capability to decrypt a Local Mode user's content. A compromised cloud operator, a subpoena to Coralswarm, a backend breach — none of these expose Local Mode user data, because the keys live only on the user's device(s). The no-training commitment applies to managed-LLM-mode synthesis the same way as elsewhere; users wanting full air-gap also configure Local Model mode (Ollama or similar) to eliminate LLM-API egress entirely.
Engineering shape The Rust core re-targets to client devices:
— Native Mac: static library + C header via cbindgen, consumed by Swift.
— iOS: same SPM package as Native Mac.
— Android: Kotlin bindings via Mozilla's UniFFI.
Web: not supported in Local Mode (WASM build is the v1.x-considered-and-deferred path; revisit only if web demand is strong).
Storage moves to per-device SQLite + sqlite-vec; embedding model bundles with the install (~30MB for bge-small).
Trade-offs the user accepts Larger install size (~200–300MB on Mac, ~50–100MB on mobile after embedding model).
Higher hardware floor (Apple Silicon Mac, modern flagship phones — older hardware may run embedding inference too slowly to feel good).
Cross-device sync becomes the user's problem: a Local Mode user with two laptops needs to sync between them via the cloud (encrypted bundle exchange) — slower than the cloud-primary instant cross-device experience.
Embedding model upgrades require client re-embed work on each device (vs one backend re-embed in cloud mode).
Mixed-mode teams A team can have both cloud-mode and Local Mode members. The cloud backend serves both: cloud-mode members query the backend directly; Local Mode members receive encrypted bundles and query their on-device copy. Co-presence works for both — for Local Mode recipients, the cloud queues encrypted bundles addressed to their device, decrypted on-device on next sync.
When it ships Demand-driven, not roadmap-driven. v1 ships in cloud-primary form. If a meaningful segment of paying users — particularly in regulated industries (legal, healthcare, finance, defense) — surfaces during early adoption asking for strict E2E, Local Mode becomes a priority for v2 or earlier. If nobody asks, it sits as a designed but unbuilt option until the case forces it.
Pricing positioning Likely an Enterprise-tier feature, possibly an add-on to Paid Team. Local Mode's natural audience overlaps strongly with enterprise buyers who need SOC 2 + SSO + audit anyway — bundling them is clean. Pricing TBD until customer conversations clarify what the segment will pay.
Mac native as the launch surface If Local Mode ships, Mac native is the strongest first surface: Mac users in privacy-sensitive professions are well-represented in Coralswarm's beachhead market, Apple Silicon has the hardware for on-device embedding inference, and the Swift code path for the Rust core is the most mature among the client targets. iOS Local Mode follows once Mac native is stable.

Native Mac App (Swift)

There is no desktop client today: ADR 0015 (docs/decisions/0015-retire-desktop-app.md) retired it on 2026-10-28. A native Mac app would be a new decision on top of that ADR; this subsection records the case for one.

A Mac app would warrant a dedicated native Swift / SwiftUI build. Mac is a disproportionately important platform for Coralswarm's target users — software teams, design teams, creative studios, parts of professional services — and Mac users have higher native-feel expectations than other platforms. A Swift Mac app unlocks: deeper system integration (Spotlight indexing, Quick Look previews, Services menu, native menu-bar presence, vibrancy effects), tighter command-bar UX, native TCC permission flows, and the option to lean on Apple Silicon's Neural Engine for local embedding inference.

Mac native would run the Rust core locally for E2E retrieval. This is different from iOS, which is a thin client calling the cloud query engine. So the code-share story with iOS is more modest than originally projected: substantial SwiftUI UI overlap, partial overlap on the data and navigation layer, but the FFI-to-Rust-core code is Mac-only. Realistic Swift code reuse with iOS: maybe 40–50%, not 60–80%.

Timing. The iOS Swift investment in v1.5 still helps — Swift team expertise carries over, SwiftUI components carry over, design language carries over. The Rust FFI work is the bigger Mac-native-specific lift. Realistic landing point: v1.7–v1.8.

Open Questions

These are the decisions that are not yet made. Documenting them explicitly so they don't get decided by default.

Technical open questions
Cross-device sync Resolved by the cloud-primary architecture. A user's personal reef lives in the cloud, so all their devices see the same graph in real time without a sync layer between them. The previous open question — how to move a personal reef between work and personal machines — became moot when the architecture moved to cloud-primary. Local Mode users will face this question (a Local Mode personal reef is per-device by default), and it's a real Local Mode design issue when that ships.
In-person and non-API meeting capture (v1.x) Committed for v1.x: screen recording + Whisper as a capture path independent of meeting platform APIs. Under v1's cloud-primary architecture, the question of where Whisper runs becomes a real design decision: (a) Audio captured on-device via OS audio APIs (ScreenCaptureKit / WASAPI loopback), streamed to the cloud backend over an authenticated channel, transcribed server-side with Whisper. Cleaner privacy story than sending the audio outside Coralswarm's stack, but audio briefly leaves the device. (b) Audio captured AND transcribed on-device via local Whisper (whisper.cpp), only the transcript is sent up. Audio never leaves the user's machine — strongest privacy. Trade-off: bundles Whisper with a local capture client (~100–500MB depending on model size) or downloads it lazily on first capture; cold-machine transcription performance is hardware-dependent. Leaning toward (b) for the privacy story; needs a real call before building.
Meeting platform API rate limits and costs Zoom transcript API has rate limits and tiered access (some endpoints are Pro/Business+ only). Microsoft Graph for Teams transcripts requires admin consent at the tenant level for some operations. Google Meet transcript API requires Workspace Business Standard+ on the user's side. Need a clear matrix of which Coralswarm features require which platform tier, surfaced honestly at signup so users know if their plan unlocks meeting capture.
Email future-reply mechanics Decided: polling, not webhooks. Triggered on a periodic cadence and on demand — not on app open. Webhooks require an HTTPS endpoint to receive callbacks. Under cloud-primary architecture, the backend has one — so webhook receive is technically possible — but it brings expiring watches (7d Gmail, 3d Graph), renewal cron jobs, and a per-user subscription registry into the architecture. The latency cost of polling (~10–15 min while the app is running, instant on manual Sync) is invisible at the use-case level: email auto-capture is not a notification system. Two triggers in v1: (1) periodic poll on a fixed cadence (run by the cloud backend using the user's stored OAuth tokens), (2) on-demand "Sync this thread now" from the email add-in. App-open is deliberately not a trigger — opening the app is not, by itself, an ingestion intent. Manual Sync is one click away for users who want immediate freshness. Webhooks remain an option for v1.x if a real workflow demands near-real-time ingestion.
Embedding model bge-small (384d) vs nomic-embed-text (768d). bge-small is faster and smaller; nomic is higher quality. Run evaluation on sample data before shipping. Decision needed before building the atom store schema (vector dimension is fixed at schema creation).
Team key rotation Under v1's server-held team key model, rotation is a backend job: the backend generates a new key, re-encrypts the team reef under the new key, and updates each remaining member's authorization envelope. No client involvement, no waiting for "the next active member to open the app." Rotation triggers: member offboarding, periodic policy (e.g. annually), explicit admin request. Open detail: do we re-encrypt the full reef on every rotation, or use a forward-secrecy scheme where new content uses the new key and old content keeps its original key? Trade-off is between simplicity (full re-encrypt) and rotation cost on large team reefs (multi-GB re-encrypt is expensive). Need to decide before offboarding workflow ships.
Decision quality How noisy will extracted decision candidates be? Unknown until we have real data. May need a quality threshold (only surface candidates above a confidence score) or a per-user tuning model. Reserve capacity in the extraction pipeline for this.
Drift threshold Cosine distance threshold for the entity drift indicator (section 08). Too sensitive → drift flag on every entity, ignored as noise. Too lax → real drift never surfaces. Needs empirical tuning on real data. Affects whether the drift feature is useful or invisible.
Decided_at override UX When the auto-extracted decided_at is wrong (the meeting happened on May 3 but the actual decision was made over Slack on May 5), how does the user correct it? Inline edit on the decision node? A separate "this decision was actually made on..." prompt during decision review? Affects how trustworthy decided_at becomes as the foundation of the whole temporal layer.
Product / business open questions
Co-presence pricing Decided: email summary + 7-day free trial. When a paying Coralswarm user ingests an event with non-user participants (their emails are in the event metadata), Coralswarm sends those non-users an email summarizing the value proposition — "you've been in N meetings / M email threads where colleagues are documenting context with Coralswarm. Sign up to access them." The email is a value pitch, not a content sample (no snippets from captured meetings — keeps the email surface clean and avoids cross-team data leakage). On signup, the new user gets a 7-day free trial with full Paid-tier access: unlimited atoms, mobile + web access, and the full co-presence backfill of events colleagues have already ingested. At trial end, the user converts to paid or drops to the free tier (capped — see Pricing Tiers), with a "download your data" option for anything beyond the free cap. Email cadence and dedup details are implementation: sensible default is one email on first co-presence event per recipient, weekly digest after, auto-stop after 4 weeks without signup.
Personal graph ownership at termination If a user stops paying, what happens to their personal graph? Read-only for 90 days → export → delete? This needs to be in the ToS before launch.
Legal review Meeting consent flow needs legal review before GA. Two-party consent jurisdictions (CA, FL, MD, IL) and GDPR are the critical ones. The announcement model likely satisfies most — but needs a real lawyer to confirm, not a founder's read.
Web query model Decided: server-side retrieval on every v1 surface, including web. Under v1's cloud-primary architecture every client (web, CLI, MCP, and the planned mobile apps) calls the same cloud query API. No client runs the Rust core locally for retrieval in v1. The substantive privacy promise — no training on user data, encrypted at rest, decrypted only during the active session — applies uniformly across surfaces. Strict E2E returns as Local Mode (see v2 Roadmap). See Privacy and Data Use in Architecture Overview.
Offline mobile query Decided: thin-client mobile apps. Offline behavior is read-only browsing of cached recently-viewed nodes; new queries require connectivity. Mobile shares the v1 architecture of every other client — only Local Mode (future) restores fully on-device retrieval. If "I want to query my reef on a flight with no wifi" becomes a meaningful user complaint, it's a Local Mode argument, not a separate mobile-specific build.
